# Chapter 1: RTOS 개요 및 FreeRTOS 소개

---

## 머리말

본 장에서는 실시간 운영체제(Real-Time Operating System, RTOS)의 근본적인 개념과 FreeRTOS의 역사적 배경 및 아키텍처에 관하여 심도 있게 살펴보기로 한다. 단순히 용어의 정의나 기능의 나열에 그치지 않고, 왜 RTOS가 현대의 임베디드 시스템에서 필수불가결한 존재가 되었는지, 그 배후에 어떠한 공학적 당위성이 존재하는지를 논리적으로 추적하는 것에 주안점을 두도록 한다.

---

## 1.1 실시간 운영체제(RTOS)란?

### 1.1.1 공학적 당위성과 역사적 배경

현대의 임베디드 시스템에서 실시간 운영체제(RTOS)의 역할은 거의 절대적이다. 자동차의 엔진 제어 유닛(Engine Control Unit, ECU), 항공기의 비행 제어 시스템(Flight Control System), 의료 기기의 생명 유지 장치에 이르기까지, 인간의 생명과 안전이 직접적으로 관련된 시스템들은 하나같이 **실시간성(Real-Time Property)**이라는 근본적인 요구 사항을 충족해야 한다. 즉 RTOS가 아니라면 현대의 미션 크리티컬(Mission-Critical) 시스템은 원천적으로 성립할 수 없다고 해도 과언이 아니다.

역사적으로 살펴보면, 초기 임베디드 시스템은 단일 제어 루프(Super Loop) 구조로 동작하였다. 메인 함수 내에서 무한 루프를 돌며 입력을 확인하고 출력을 갱신하는 이른바 '폴링(Polling)' 방식이었다. 그러나 시스템의 복잡도가 증가하고, 다수의 독립적인 기능이 동시에 수행되어야 하는 상황이 도래하면서, 단일 루프 구조는 근본적인 한계에 직면하게 되었다. 각 기능의 실행 주기를 정밀하게 제어하기 어렵고, 한 기능의 처리 지연이 다른 모든 기능에 연쇄적인 영향을 미치는 문제가 발생하였다. 이러한 현상의 배후에서 RTOS의 필요성이 대두되었으며, 1970년대 이후로 VxWorks, QNX, μC/OS 등 다양한 상용 RTOS가 등장하여 산업계의 요구에 부응하게 되었다.

### 1.1.2 실시간성의 물리적 원리

그렇다면 실시간성이란 정확히 무엇을 의미하는가? 이 개념의 배후에는 **'예측 가능성(Predictability)'**이라는 핵심적인 공학적 원리가 존재한다. 범용 운영체제(General-Purpose Operating System)가 평균적인 처리량(Throughput)의 극대화를 목표로 한다면, 실시간 운영체제는 **최악의 경우(Worst Case)**에도 주어진 시간 제약(Time Constraint) 내에 반드시 응답을 완료할 것을 보장해야 한다. 

이를 수식으로 표현하면 다음과 같다:

$$
WCET \leq D
$$

여기서 $WCET$(Worst-Case Execution Time)는 해당 태스크가 최악의 조건에서도 완료되기까지 소요되는 최대 시간을 의미하며, $D$(Deadline)는 시스템이 요구하는 응답 시한을 나타낸다. 이 부등식은 물리적으로 태스크의 실행 시간이 어떠한 상황에서도 데드라인을 초과해서는 안 된다는 것을 나타내는 핵심적인 관계식이다. 따라서 단순히 빠른 처리를 추구하는 것에 그치지 않고, 정해진 시간 내에 확정적으로(Deterministically) 응답함으로써 시스템의 신뢰성을 담보하는 것이 RTOS의 본질적 사명이라 할 수 있다.

### 1.1.3 경성 실시간과 연성 실시간

RTOS는 크게 **경성 실시간(Hard Real-Time)**과 **연성 실시간(Soft Real-Time)**의 두 가지 범주로 구분된다. 경성 실시간 시스템에서는 시간 제약의 위반이 곧 시스템의 치명적 실패를 의미하는데, 자동차 에어백 전개 장치가 10밀리초의 시간 제약을 어길 경우 탑승자의 안전을 보장할 수 없게 되는 것이 대표적인 사례이다. 이 경우 데드라인 미스(Deadline Miss)의 비용은 무한대로 간주된다.

반면 연성 실시간 시스템에서는 시간 제약의 위반이 서비스 품질(Quality of Service)의 저하를 야기할 뿐 시스템 자체의 파국으로 이어지지는 않는다. 동영상 스트리밍에서 간헐적으로 발생하는 프레임 드롭(Frame Drop)이 이에 해당하며, 사용자 경험의 저하는 있을지언정 시스템 전체의 안전성이 위협받지는 않는다.

따라서 개발하고자 하는 시스템의 실시간 요구 수준이 어느 범주에 속하는지를 명확히 규정하는 것이 RTOS 기반 설계의 첫걸음이라 할 수 있다. 이 결정에 따라 스케줄링 알고리즘의 선택, 최악 실행 시간 분석의 정밀도, 그리고 시스템 검증의 수준이 달라지게 된다.

## 1.2 FreeRTOS의 역사와 특징

### 1.2.1 탄생과 발전

FreeRTOS는 2003년 Richard Barry에 의해 처음 공개된 이래로 지난 20여 년간 세계에서 가장 널리 사용되는 실시간 운영체제로 성장하였다. 2017년 Amazon Web Services(AWS)에 인수되어 현재는 AWS IoT 생태계의 핵심 구성 요소로 자리매김하고 있으나, 그 핵심인 FreeRTOS 커널은 여전히 MIT 오픈소스 라이선스 하에서 자유롭게 사용 가능하다. 이러한 역사적 배경은 FreeRTOS가 학술적 연구 목적뿐만 아니라 상업적 제품 개발에서도 제약 없이 활용될 수 있음을 의미한다.

FreeRTOS의 성공 요인 중 하나는 그 핵심 커널이 극도로 간결하면서도 필수적인 기능을 빠짐없이 제공한다는 점에 있다. 자동차 산업의 기능 안전 표준인 IEC 61508 및 ISO 26262에 대한 인증 지원 버전인 SAFERTOS도 존재하며, 이는 FreeRTOS의 설계 원칙이 미션 크리티컬 도메인에서도 신뢰할 수 있음을 입증하는 것이다.

### 1.2.2 설계 철학: 최소주의와 이식성

FreeRTOS의 설계 철학은 **최소주의(Minimalism)**와 **이식성(Portability)**이라는 두 가지 원칙에 기반한다. 커널 자체는 약 9,000줄 남짓의 C 코드로 구성되어 있어, 그 내부 동작 원리를 완전히 이해하는 것이 현실적으로 가능하다. 이는 상용 RTOS들이 수십만 줄에 달하는 코드베이스를 지니고 있어 그 전모를 파악하기 어려운 것과 대조적이다. 

이러한 간결성은 다음과 같은 공학적 이점을 제공한다:

1. **코드 감사(Code Audit)의 용이성**: 보안 및 안전 관점에서 전체 코드를 검토하는 것이 현실적으로 가능하다.
2. **메모리 풋프린트 최소화**: 수 킬로바이트의 ROM/RAM만으로도 RTOS 운용이 가능하다.
3. **학습 접근성**: 커널 동작을 소스 레벨에서 완전히 이해하는 것이 교육적으로 가능하다.

또한 FreeRTOS는 하드웨어 의존적인 부분을 **포팅 레이어(Portable Layer)**로 철저히 분리함으로써, ARM Cortex-M, RISC-V, Infineon TriCore, Renesas RH850 등 40여 개 이상의 마이크로프로세서 아키텍처에서 동일한 커널 코드를 사용할 수 있도록 설계되었다. 이러한 구조적 분리는 새로운 아키텍처로의 이식 시 수정해야 할 코드 범위를 명확히 한정함으로써, 포팅 작업의 예측 가능성과 효율성을 크게 향상시킨다.

### 1.2.3 핵심 기능

FreeRTOS가 제공하는 핵심 기능들을 살펴보면, 먼저 **우선순위 기반 선점형 스케줄링(Priority-Based Preemptive Scheduling)**을 통해 가장 높은 우선순위를 가진 Ready 상태의 태스크가 언제든지 CPU를 점유할 수 있도록 보장한다. `FreeRTOS에서는 숫자가 클수록 높은 우선순위를 갖는다`는 점에 주의할 필요가 있다. `configMAX_PRIORITIES` 설정에 따라 사용 가능한 우선순위 레벨이 결정되며, 우선순위 0은 Idle 태스크용으로 예약되어 있다.

동일 우선순위의 태스크들 사이에서는 **라운드 로빈(Round-Robin)** 방식의 시간 분할이 적용되어 공정한 CPU 자원 배분이 이루어진다. 이는 `configUSE_TIME_SLICING` 설정을 통해 활성화되며, 각 틱(Tick) 발생 시 동일 우선순위의 다음 태스크로 실행이 전환된다.

태스크 간 통신 및 동기화를 위해서는 다음과 같은 프리미티브(Primitive)들이 제공된다:

| 프리미티브             | 용도             | 특징                        |
| ---------------------- | ---------------- | --------------------------- |
| **Queue**              | 데이터 전달      | FIFO 기반, 블로킹 지원      |
| **Binary Semaphore**   | 이벤트 동기화    | ISR-Task 간 통신에 적합     |
| **Counting Semaphore** | 리소스 카운팅    | 다중 인스턴스 관리          |
| **Mutex**              | 상호 배제        | 우선순위 상속 메커니즘 내장 |
| **Event Group**        | 다중 이벤트 대기 | AND/OR 조합 대기 가능       |
| **Task Notification**  | 경량 동기화      | 별도 객체 불필요, 고성능    |

이들 각각의 내부 구현과 적합한 사용 시나리오를 이해하는 것이 FreeRTOS 숙달의 핵심이라 할 수 있으며, 이에 관해서는 후속 장에서 상세히 다루기로 한다.

## 1.3 FreeRTOS 아키텍처 개요

### 1.3.1 계층적 구조

FreeRTOS의 아키텍처를 이해하기 위해서는 그 계층적 구조에 주안점을 두도록 한다. FreeRTOS는 크게 네 개의 논리적 계층으로 구분될 수 있다.

```
┌─────────────────────────────────────────────────────┐
│              응용 계층 (Application Layer)           │
│     사용자 태스크, 응용 로직, API 호출              │
├─────────────────────────────────────────────────────┤
│              커널 계층 (Kernel Layer)                │
│   tasks.c, queue.c, timers.c, event_groups.c 등    │
├─────────────────────────────────────────────────────┤
│             포팅 계층 (Portable Layer)               │
│      port.c, portmacro.h (아키텍처별 구현)          │
├─────────────────────────────────────────────────────┤
│       하드웨어 추상화 계층 (HAL Layer)               │
│           GPIO, UART, Timer 등 드라이버             │
└─────────────────────────────────────────────────────┘
```

최상위에는 **응용 계층(Application Layer)**이 위치하며, 이는 개발자가 작성하는 태스크(Task)들과 응용 로직으로 구성된다. 그 아래에는 **커널 계층(Kernel Layer)**이 존재하는데, `tasks.c`, `queue.c`, `timers.c`, `event_groups.c` 등의 핵심 모듈이 스케줄링, 태스크 간 통신, 시간 관리 등의 기능을 제공한다. 커널 계층 하부에는 **포팅 계층(Portable Layer)**이 위치하여 특정 프로세서 아키텍처에 종속적인 컨텍스트 스위칭(Context Switching), 인터럽트 제어, 임계 구역(Critical Section) 관리 등을 담당한다. 마지막으로 **하드웨어 추상화 계층(Hardware Abstraction Layer)**이 GPIO, UART, Timer 등 실제 주변 장치와의 인터페이스를 제공한다.

이러한 계층 구조의 배후에는 **'관심사의 분리(Separation of Concerns)'**라는 소프트웨어 공학의 근본 원칙이 존재한다. 응용 개발자는 커널 내부의 복잡한 스케줄링 알고리즘을 알 필요 없이 `xTaskCreate()`, `xQueueSend()` 등의 API를 통해 원하는 기능을 사용할 수 있다. 마찬가지로 커널 개발자는 하드웨어별 레지스터 조작의 세부 사항을 포팅 레이어에 위임함으로써 아키텍처 독립적인 로직에 집중할 수 있다. 따라서 FreeRTOS의 아키텍처를 이해한다는 것은 각 계층의 책임과 그들 사이의 인터페이스를 명확히 인식하는 것을 의미한다.

### 1.3.2 Ready List 자료구조

커널 계층에서 가장 중요한 자료구조 중 하나는 **Ready List**이다. FreeRTOS는 우선순위 수(`configMAX_PRIORITIES`)만큼의 이중 연결 리스트(Doubly Linked List) 배열인 `pxReadyTasksLists`를 유지하며, 각 태스크는 자신의 우선순위에 해당하는 리스트에 삽입된다.

```c
// tasks.c의 핵심 데이터 구조
PRIVILEGED_DATA static List_t pxReadyTasksLists[ configMAX_PRIORITIES ];
```

스케줄러는 이 배열을 가장 높은 인덱스부터 순회하여 비어 있지 않은 첫 번째 리스트에서 다음 실행 태스크를 선택한다. 이 알고리즘은 다음과 같이 구현된다:

```c
#define taskSELECT_HIGHEST_PRIORITY_TASK()                          \
{                                                                    \
    UBaseType_t uxTopPriority = uxTopReadyPriority;                 \
    while( listLIST_IS_EMPTY( &pxReadyTasksLists[ uxTopPriority ] ) ) \
    {                                                                \
        --uxTopPriority;                                            \
    }                                                                \
    listGET_OWNER_OF_NEXT_ENTRY( pxCurrentTCB,                       \
                                 &pxReadyTasksLists[ uxTopPriority ] ); \
}
```

이 매크로는 물리적으로 가장 높은 우선순위의 비어있지 않은 리스트를 찾아 그로부터 다음 실행할 태스크를 선택하는 핵심적인 스케줄링 연산을 구현한다. 이 메커니즘은 O(1) 시간 복잡도의 스케줄링을 가능하게 하며(우선순위 수가 상수이므로), 이는 실시간 시스템에서 요구되는 결정론적 동작의 핵심적인 기반이 된다.

### 1.3.3 태스크 상태 머신

FreeRTOS의 태스크는 다음 네 가지 상태 중 하나에 존재하며, 상태 간 전이는 커널에 의해 관리된다:

```
                    ┌───────────┐
         ┌─────────→│  Running  │←─────────┐
         │          └─────┬─────┘          │
         │                │                │
    vTaskResume()    vTaskDelay()    Context Switch
    이벤트 발생       xQueueReceive()   (더 높은 우선순위 Ready)
         │           (블로킹)             │
         │                │                │
         │                ▼                │
┌────────┴───────┐  ┌───────────┐  ┌───────┴────────┐
│   Suspended    │  │  Blocked  │  │     Ready      │
│ (일시 정지)    │  │ (대기 중) │  │ (실행 대기)    │
└────────────────┘  └───────────┘  └────────────────┘
         ▲                │                ▲
         │                │                │
    vTaskSuspend()   타임아웃 만료      xTaskCreate()
         │           이벤트 수신           │
         │                │                │
         └────────────────┴────────────────┘
```

**Running** 상태의 태스크는 현재 CPU를 점유하고 실행 중인 태스크이다. 시스템에서는 CPU 코어당 하나의 태스크만이 Running 상태에 있을 수 있다. **Ready** 상태의 태스크는 실행 준비가 완료되어 Ready List에 삽입되어 있으나 아직 스케줄러에 의해 선택되지 않은 태스크를 의미한다. **Blocked** 상태는 특정 이벤트(시간 경과, 큐 데이터 도착 등)를 기다리는 태스크의 상태이며, **Suspended** 상태는 명시적으로 `vTaskSuspend()` 호출에 의해 정지된 태스크의 상태이다.

## 1.4 TriCore 포팅 레이어 소개

### 1.4.1 TriCore 아키텍처의 특성

Infineon TriCore 아키텍처는 자동차용 마이크로컨트롤러 시장에서 지배적인 위치를 점하고 있으며, 특히 AURIX™ 제품군은 ISO 26262 ASIL-D 수준의 기능 안전성을 요구하는 파워트레인, 섀시, ADAS 애플리케이션에서 널리 채택되고 있다. 본 교재에서는 TC387을 대상 플랫폼으로 하여 FreeRTOS의 동작을 분석하므로, TriCore 특유의 하드웨어 메커니즘에 대한 이해가 선행되어야 한다.

TriCore 아키텍처의 가장 독특한 특징 중 하나는 **컨텍스트 저장 영역(Context Save Area, CSA)**의 존재이다. 일반적인 프로세서에서는 컨텍스트 스위칭 시 소프트웨어가 모든 레지스터를 명시적으로 스택에 저장하고 복원해야 한다. 그러나 TriCore는 하드웨어적으로 CSA라 불리는 전용 메모리 영역을 관리하며, 함수 호출이나 인터럽트 발생 시 상위 컨텍스트(Upper Context) 또는 하위 컨텍스트(Lower Context)를 자동으로 저장한다.

| 컨텍스트 유형 | 저장되는 레지스터            | 저장 트리거          |
| ------------- | ---------------------------- | -------------------- |
| Upper Context | A[10-15], D[8-15], PSW, PCXI | CALL, RET, Interrupt |
| Lower Context | A[2-7], D[0-7], A[11] (RA)   | 명시적 SVLCX 명령    |

이러한 하드웨어 지원 메커니즘은 컨텍스트 스위칭의 지연 시간(Latency)을 현저히 감소시키며, 이는 실시간 시스템의 응답성 향상에 직접적으로 기여한다.

### 1.4.2 FreeRTOS TriCore 포트 구현

FreeRTOS의 TriCore 포트는 이러한 하드웨어 특성을 최대한 활용하도록 설계되어 있다. `port.c` 파일에 구현된 `pxPortInitialiseStack()` 함수는 태스크 생성 시 초기 CSA 체인을 구성하며, 태스크가 처음 스케줄링될 때 마치 인터럽트로부터 복귀하는 것처럼 자연스럽게 실행을 시작할 수 있도록 컨텍스트를 설정한다. 

```c
// TriCore 포트의 컨텍스트 스위칭 트리거
void vTaskSwitchContext( void )
{
    if( uxSchedulerSuspended != ( UBaseType_t ) 0U )
    {
        xYieldPending = pdTRUE;
    }
    else
    {
        xYieldPending = pdFALSE;
        taskSELECT_HIGHEST_PRIORITY_TASK();  // 핵심!
    }
}
```

또한 `portYIELD()` 매크로는 TriCore의 소프트웨어 트랩(Software Trap)을 통해 컨텍스트 스위칭을 트리거하며, 이 과정에서 현재 태스크의 CSA는 자동으로 보존된다.

### 1.4.3 시스템 틱 생성

시스템 틱(System Tick)의 생성은 TriCore의 STM(System Timer Module)을 활용하여 구현된다. `configTICK_RATE_HZ`에 정의된 주기(일반적으로 1000Hz, 즉 1ms)로 인터럽트가 발생하면, `xPortSysTickHandler()`가 호출되어 시간 관리와 스케줄링 트리거를 수행한다.

틱 인터럽트에서 수행되는 주요 작업은 다음과 같다:

1. **틱 카운터 증가**: 시스템 시간 관리를 위한 `xTickCount` 증가
2. **지연 리스트 확인**: 타임아웃이 만료된 태스크를 Ready 리스트로 이동
3. **스케줄링 판단**: 더 높은 우선순위의 태스크가 Ready 상태가 되었는지 확인
4. **컨텍스트 스위칭 요청**: 필요시 `portYIELD_FROM_ISR()` 호출

이처럼 포팅 레이어는 FreeRTOS 커널과 TriCore 하드웨어 사이의 가교 역할을 담당하며, 그 구현 세부 사항을 이해하는 것이 본 교재의 심화 학습 목표 중 하나라 할 수 있다.

## 핵심 정리

본 장에서 다룬 내용을 정리하면 다음과 같다:

1. **RTOS의 본질**: 평균적 성능이 아닌 최악의 경우에도 데드라인을 준수하는 예측 가능성이 RTOS의 핵심 가치이다.

2. **실시간성의 분류**: 경성 실시간과 연성 실시간의 구분에 따라 시스템 설계 접근법이 달라진다.

3. **FreeRTOS의 설계 철학**: 최소주의와 이식성을 통해 광범위한 적용성과 깊은 이해 가능성을 동시에 달성한다.

4. **계층적 아키텍처**: 관심사의 분리 원칙에 따라 응용, 커널, 포팅, HAL 계층으로 구성된다.

5. **TriCore의 특성**: CSA 기반의 하드웨어 컨텍스트 저장 메커니즘은 효율적인 컨텍스트 스위칭을 가능하게 한다.
